## 核心论点
长期运行代理（横跨多个上下文窗口、需要数小时甚至数天）的真正瓶颈不是模型能力，而是**管理工具（harness）设计**。Claude Agent SDK 靠 compaction 仍不够：默认提示下，连 Opus 4.5 也做不出生产级应用。解法是双代理结构——**初始化代理**在首次会话铺好环境，**编码代理**在每次会话做**增量进展并留下清晰工件**。

## 要点摘录

### 两个失败模式
1. **一次做完（one-shot）**：代理试图一口气实现整个应用 → 中途上下文耗尽 → 留下半实现、无文档的功能 → 下一会话只能猜，浪费时间重建基础。
2. **过早宣布胜利**：项目后期，新会话发现"已有进展"就宣告完成，明明功能缺失。

### 双重解决方案
- **初始化代理**（首个会话）：用专门提示设置初始环境——
  - `init.sh`（启动开发服务器等环境操作）；
  - `claude-progress.txt`（各代理做了什么事的日志）；
  - 初始 git commit；
  - **功能列表文件**：把需求扩展为端到端特性清单（claude.ai 克隆例：200+ 条），全部标记 `passes: false`，让后续代理看清"完整功能长什么样"。
- **编码代理**（后续每次会话）：一次只做一个功能，结束时保持**整洁状态**——"适合合并到主分支的代码：无重大 bug、有序、有文档，开发者可不用先清理烂摊子就开新功能"。

### 关键技巧
- **功能列表用 JSON**：模型改 JSON 文件比 Markdown 更不容易越界；只允许改 `passes` 字段，配套强措辞"删除或修改测试不可接受"。
- **增量进度 + 版本控制**：要求每次改动后以描述性信息 git commit + 写进度文件 → 可回滚坏代码、恢复可用状态，也消除了"猜发生了什么"的浪费。
- **端到端测试**：Claude 倾向"改完代码、单元测试/curl 通过"就标完成，却没发现功能端到端不可用。显式要求用浏览器自动化（Puppeteer MCP）**以人类用户身份**测试后，性能大幅提升。局限：视觉限制导致看不到浏览器原生 alert 弹窗等。

### 会话起步程序（Getting up to speed）
每次新会话开场固定走：
1. `pwd` 确认工作目录；
2. 读 git 日志 + 进度文件；
3. 读功能列表，挑**优先级最高、未完成**的功能；
4. 读/跑 `init.sh`，先跑一遍基础端到端测试——确认应用没坏，再动工。

### 四类失败与对策（原文表格摘要）
| 失败模式 | 初始化代理对策 | 编码代理对策 |
|---|---|---|
| 过早宣告项目完成 | 建功能列表文件 | 开场读列表，一次只做一个功能 |
| 环境留下 bug / 未记录进展 | 建 git + 进度笔记 | 开场读进度+日志+基础测试；结束写 commit+进度 |
| 过早把功能标为完成 | 建功能列表 | 仔细测试后才标 `passes` |
| 花时间摸索如何启动应用 | 写 `init.sh` | 开场就读 `init.sh` |

### 未来工作
- 未决：单一通用编码代理 vs **专业化多代理**（测试代理/QA/代码清理）谁更强。
- 未证：这些经验能否推广到科学研究、财务建模等非全栈 Web 场景。
