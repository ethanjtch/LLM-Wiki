## 核心论点
LLM 与文档的常规用法（RAG：上传文件、查询时检索、每次重新生成答案）"没有知识积累"。更好的模式是让 LLM **增量构建并持续维护一个持久的 wiki**：每次摄入新来源时不仅索引它，还读取、提取、整合进现有 wiki 页，编译一次并持续保鲜，而非每次查询都重推。**wiki 是一个持续复利（compounding）的工件**——交叉引用已在、矛盾已标、综合已反映读过的一切。

## 要点摘录

### 与 RAG 的本质差异
| | RAG | LLM Wiki |
|---|---|---|
| 知识状态 | 每次查询从源头重新推导 | 编译一次、持续更新 |
| 积累 | 无（每问都从零重新拼装） | 复利（每加一来源、每问一问题都更丰富） |
| 职责分担 | 人上传、模型检索生成 | 人负责找源与提问，模型负责全部 整理（bookkeeping） |
| 交叉引用/矛盾 | 每次现场找 | 已存在、已标定 |

### 三层架构
1. **Raw sources 原始来源**：人精选的文档合集，不可变，LLM 只读不改——真相源头。
2. **The wiki wiki 层**：LLM 生成的 markdown 目录，模型全权所有（建页、更新、交叉引用、一致性）。
3. **The schema 架构层**：CLAUDE.md / AGENTS.md 告诉 LLM wiki 结构、约定、工作流——**这是让 LLM 成为"有纪律的维护者"而非"普通聊天机器人"的关键配置文件**，随时间与人共同演化。

### 三种核心操作
- **Ingest（摄入）**：读源 → 讨论要点 → 写摘要页 → 更新索引/实体/概念页 → 追加 log。单个来源可触及 10-15 页。可单源深交互，也可批量少监督。
- **Query（问答）**：先读 index 定位 → 下钻阅读 → 带引用作答。**好答案应归档回 wiki 作为新页**（对比表、分析、发现的连接），不让探索消失在聊天里。
- **Lint（体检）**：周期性健康检查——页间矛盾、被新源取代过时的说法、无入链孤儿页、被提到但缺页的概念、缺失交叉引用、数据缺口。

### 索引与日志
- `index.md`：内容导向目录，每页链接+一行摘要+元数据，按类分组。较小时（~100 来源、数百页）足够定位页面，**可避免 embedding RAG 基建**。
- `log.md`：时间导向，append-only。统一前缀 `## [YYYY-MM-DD] ingest | 标题` → 可被 unix 工具 grep 解析。

### 可选工具
- 搜索：qmd（本地 markdown 搜索，BM25+向量+LLM 重排，CLI+MCP 双接口）；或自写脚本。
- Obsidian Web Clipper 剪藏、本地下载附件（`raw/assets/`）、Graph view 看结构、Marp 幻灯片、Dataview 查 frontmatter。
- wiki 就是一个 git 仓库：免费获得版本历史、分支、协作。

## 为什么有效
维护知识库的繁琐不在阅读/思考，而在 **bookkeeping（记录管理）**：更新交叉引用、保持摘要新鲜、标注新旧矛盾、维持几十页一致。人是靠这个负担增长而放弃 wiki 的；**LLM 不会无聊、不会忘更新交叉引用、一次能碰 15 个文件——维护成本趋近于零，所以 wiki 能持续被维护**。人的职责是策展来源、引导分析、提出好问题。

### 思想谱系：Memex
与 Vannevar Bush（1945）的 **Memex** 同源——个人化、主动策展、文档间连接与文档本身等值的知识库。Bush 没解决"由谁维护"，LLM 解决了。
